# Browser SSO from WSL, and how the session refreshes itself

**Date:** 2026-08-24
**Audience:** anyone reproducing this from the Windows side, or from another agent session
**Status:** working since 2026-08-21; the tracked record for the mechanics

## 1. The problem, stated exactly

Two facts collide.

**The credential lives on Windows.** A system behind Entra Conditional Access
with a device requirement is satisfied by the **Primary Refresh Token**, which
is held by the Windows account broker and bound to the machine. It is not a file
and it is not reachable from the Linux side of WSL. A browser launched under
Linux will loop on the identity provider indefinitely, and no amount of flags,
profiles or certificate handling changes that. **This is not a configuration
problem.** Recognising it as a boundary rather than a bug is the whole of step
one, and it is where hours go.

**The tool runs on Linux.** vsp is built and run under WSL.

So the browser step must execute as a **Windows process**, and only its result
may cross back.

## 2. The design that follows

```
 WSL (Linux)                              Windows
 ───────────                              ───────
 vsp                                      vsp-sso.exe
  │  stage helper onto a Windows drive ──────►│
  │                                           │ browser + PRT + IdP
  │◄────────── cookies as JSON on stdout ─────│
  │
  └─► ~/.vsp/sso/<system>.json   (0600)
```

**Nothing but cookies crosses the boundary.** No password, no token, no profile.
The helper (`cmd/vsp-sso/`, 122 lines) is a separate binary for exactly this
reason and takes every identifier by flag, so it is system-agnostic and safe to
hand to anyone.

### 2.1 Four WSL details that each cost a debugging session

| Detail | Why | Where |
|---|---|---|
| The helper is **copied to a Windows drive** before being run | Windows refuses to execute from the `\\wsl$\` UNC share in many configurations | `StageSSOHelper` |
| `cmd.exe` is invoked with `Dir = /mnt/c` | started from a Linux path it warns about the unsupported UNC working directory and pollutes stderr | `windowsEnvVar` |
| Staging is skipped when size and mtime match | otherwise several megabytes cross the 9p mount on every single run | `StageSSOHelper` |
| WSL is detected by `WSL_DISTRO_NAME`, `WSL_INTEROP`, then `/proc/sys/kernel/osrelease` | the env vars are absent under some service managers; the kernel string is not | `IsWSL` |

Paths are translated with `wslpath -u` / `wslpath -w` rather than by string
surgery, because the mount prefix is configurable.

### 2.2 Build

```bash
GOOS=windows GOARCH=amd64 go build -o vsp-sso.exe ./cmd/vsp-sso   # or: make sso-helper
```

`FindSSOHelper` looks beside the running `vsp`, then in `./build` — which is
where `make build-all` leaves it. An explicit path in the system config wins.

### 2.3 Configuration

```json
{
  "systems": {
    "devsys": {
      "url": "https://dev.example.local:44300",
      "client": "100",
      "auth": "sso"
    }
  }
}
```

`"auth": "sso"` is the whole switch. Optional under it: `trigger_url`,
`profile`, `helper_path`, `interactive`.

## 3. The trigger URL

The browser has to be sent at something that is authentication-gated and
**renders as a page**. vsp derives `/sap/bc/adt/?sap-client=NNN` by default:
every system vsp can talk to has it, it is gated, and it returns a document.

The failure mode worth knowing: point the browser at a URL the browser treats as
a **download**, and the tab stays on `about:blank` with no cookies to read. The
capture then times out for a reason that looks nothing like its cause. Systems
that gate SSO at the launchpad instead need `trigger_url` set to the Fiori URL.

## 4. Refresh — the part that is genuinely non-obvious

### 4.1 An expired SSO session does not return 401

This is the single most important fact in this document.

ICF does not reject an expired browser session. It **forwards the request to the
identity provider**, the redirect chain is followed, and a logon page arrives
under a perfectly ordinary **HTTP 200**. Any code that keys re-authentication on
a status code will therefore never re-authenticate, and will instead try to
parse an HTML logon form as ADT XML and report a nonsense error.

Detection is by two signals instead:

1. **Origin.** `redirectedAwayFromSAP` compares the *final* response URL's host
   against the configured base URL. A request that asked for an ADT resource and
   was answered by another host was answered by the IdP.
2. **A missing CSRF token.** An ADT response from SAP carries one; a logon page
   does not.

### 4.2 The loop

```
request ──► 200 + wrong origin, or 401
              │
              ▼
        ReauthFunc = provider.Refresh
              │  silent capture (45s)
              │    └─ exit code 2 ⇒ a human is needed
              │         └─ interactive ⇒ visible window (5m)
              │         └─ otherwise ⇒ error naming `vsp sso login`
              ▼
        new cookies ─► reset the cookie jar ─► fetch CSRF ─► retry
```

Three parts of that are load-bearing:

- **The cookie jar is reset, not merged.** The jar still holds what the expired
  session's server set, including its own `SAP_SESSIONID`. Left in place it
  rides along beside the new one and the server picks between them —
  intermittently, which is the worst way for this to fail.
- **`lastReauth` is stamped only after the CSRF fetch succeeds.** Stamping it
  earlier means a failed refresh silences the next caller through the cooldown.
- **Stampede protection.** Concurrent requests serialise on a mutex; the first
  refreshes and the rest, inside the cooldown, skip. `ReauthTimeout` bounds it
  so a slow IdP cannot hold the mutex indefinitely — 30s by default, and worth
  raising where a human types a second factor.

### 4.3 The cache

`~/.vsp/sso/<system>.json`, written 0600 through a temporary file, one file per
system so refreshing one never invalidates another.

**A cached session is used whatever its age.** Only the server knows when it
expired, and finding out costs a request the caller is about to make anyway.
Staleness is handled on the way back. A corrupt cache reports as absent rather
than as an error, because it is a cache.

### 4.4 The one that will bite

> **Never set `SAP_USER`/`SAP_PASSWORD` alongside SSO.**

`HasBasicAuth()` returning true disables `ReauthFunc` entirely. The result is a
session that works until it expires and then fails permanently with no
indication why. A stray variable in a shell profile is enough.

## 5. Commands

```bash
vsp -s devsys sso login     # visible browser, sign in once
vsp -s devsys sso status    # is a session cached, and how old
vsp -s devsys sso refresh   # force a silent capture
vsp -s devsys sso clear     # drop the cache
```

Exit codes from the helper: `0` captured, `2` interactive login required,
`1` anything else. `2` is what lets a caller escalate to a visible window
instead of reporting a hard failure.

## 6. If it does not work

In order, because each step rules out the one below:

1. **`vsp -s <sys> sso login`** with a window. If a human cannot sign in there,
   nothing automated will.
2. **Is WSL interop on?** `cmd.exe /C echo %TEMP%` from Linux must answer.
3. **Is the helper built for Windows?** `file vsp-sso.exe` must say PE32+.
4. **Is the trigger URL a page?** Open it in a browser by hand; if it downloads,
   set `trigger_url`.
5. **Is a basic-auth variable set?** `env | grep SAP_` — see §4.4.
6. **Does the browser see the PRT?** Sign in to any Entra-gated web app in Edge
   on the same Windows account. If that prompts, the device state is the problem
   and it is outside vsp.
