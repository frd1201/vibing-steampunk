# Post-mortem: from a dump to the statement, and to its neighbours

Status: design, grounded in what a live 7.58 system actually answers.
Steps 1 to 3 of the build order are done — `vsp dumps`, with `--group`,
`--explain` and `--similar`. Steps 4 and 5 are still design.

## Why this is worth doing

We can already drive a debugger over plain ADT and record a
statement-level trace with values. That helps when you can reproduce the
failure. Most of the time nobody can: there is a dump from Tuesday, a
user who has moved on, and no way to make it happen again.

The material for the other case turns out to be there, all of it over
plain ADT, no Z code:

| what | resource |
|---|---|
| what | resource | checked |
|---|---|---|
| runtime errors (ST22) | `/sap/bc/adt/runtime/dumps` | answers, 2.3 MB of entries |
| system log (SM21) | `/sap/bc/adt/runtime/systemmessages` | answers, empty here |
| gateway errors | `/sap/bc/adt/gw/errorlog` | answers, empty here |
| ATC findings | `/sap/bc/adt/atc/feeds/verdicts` | answers, empty here |
| RAP contract violations | `/sap/bc/adt/bo/feeds/ccviolations` | answers, empty here |
| ABAP traces (SAT) | `/sap/bc/adt/runtime/traces/abaptraces` | advertised |

`/sap/bc/adt/feeds` is the index of the feed-shaped ones.

**The application log (SLG1) has no feed** — and it turns out not to
need one.

An earlier draft listed `/sap/bc/adt/applicationlog/objects` as the
business log. It is not: it answers 400 "URI-Mapping cannot be
performed", and its discovery siblings — `$configuration`, `$schema`,
`source/formatter`, `validation` — are the signature of a repository
*object type editor*. It edits SLG0 log object definitions.

The same draft then said the log would need the `BAL_*` function modules
over RFC, and that a single-sign-on system with no gateway would have to
reach them through the WebSocket tunnel. Both halves were wrong, and the
second one hid the first: **`BAL_DB_SEARCH` cannot be called remotely at
all.** Neither the tunnel nor SOAP-RFC nor an open gateway helps, because
the blocker is not the transport — those modules are simply not
remote-enabled. A transport question was the wrong question.

The log is readable anyway, and over plain ADT: its header table is an
ordinary table, and free SQL through `/sap/bc/adt/datapreview` reads it.

```
vsp query -s <sys> balhdr --fields LOGNUMBER,OBJECT,SUBOBJECT,ALDATE,ALTIME,ALUSER,ALPROG
```

Verified on 7.58 and on 7.50. `BALHDR` carries `ALPROG` — the program
that wrote the entry — which is exactly the field the ranking below
rests on, plus the user, the timestamp and the log object.

Two limits, so this is not oversold:

- `BALDAT` is a cluster and data preview refuses it, so the message
  *bodies* are not readable this way. `BALM`, which holds message ids
  and types per log on newer releases, does answer — it is simply empty
  on the demo system, so its shape is unverified.
- Header-level is enough for correlation ("which program logged what
  object, when") and not enough to show a person the message text. If
  that is wanted, it needs the BAL API, which means Z code, because the
  standard modules cannot be reached remotely by any transport.

## Similar dumps

"Similar" is a ladder, not a boolean, and each rung is cheap because it
is category equality:

1. same error type + same program + same line — the same bug
2. same error type + same program — the same bug or its siblings
3. same error type + same application component — a neighbourhood
4. same error type — a class of failure

Grouped over a time window this answers the question people actually
have: *is this new, and how often does it happen?* "47 times in three
days, always the same line, always after 18:00, always one user" is a
different investigation from "once, ever".

### Built: `vsp dumps --similar <id|latest>`

All four rungs are implemented. What the design got right is that the
rungs are equality on fields we already have; what it did not say is
that they are not equally cheap. Rungs 2 and 4 are pure feed and cost
nothing. Rungs 1 and 3 need the failing line and the application
component, and **neither is in the structured detail document** — the
XML at `/runtime/dump/<id>` has the error, the author, the exception
class and the terminated program as attributes, and hides the
termination line in a link fragment (`...#start=36`), but it has no
application component at all. Both come out of `/formatted`, which is
45 KB to 850 KB of text per dump, one fetch per candidate. So the
expensive half is budgeted (`--deep`, default 25) and the cheap half
always runs.

Four things the live system said that the design did not:

- **A line is not a position without its include.** Three different
  function groups on 7.58 all terminate at `SAPMSSY1` line 36 — that is
  the RFC entry point, not their bug. Rung 1 is error + program +
  include + line, and those three stay on rung 4 where they belong.
- **"Not assigned" is not a component.** Custom code usually has none,
  and treating the words as a value would put every unassigned object
  in the system into one neighbourhood. It is normalised to empty and
  the rung is dropped rather than faked. Rung 3 still fires usefully
  where the dump is filed under a standard program: three unrelated
  programs, two of them `Z*`, all came back under `BC-MID-RFC`.
- **The component belongs to the header program, which is not always
  the terminated program.** On a `RAISE_EXCEPTION` the feed names the
  standard class that raised and the dump header names the custom
  caller — so a standard SAP class can show "no component" and it is
  the caller's component that is missing. The output says which
  program the component is filed under when the two differ.
- **The header table's rows vary by dump category.** "ABAP programming
  error" carries program and component, "Internal error" carries the
  component only, "Resource bottleneck" carries neither. Read by
  label; read by row number and every value shifts.

Two parsing traps, both from live text and both silent rather than
loud: the sentence carrying the failing line wraps *between the number
and the include*, so a line-by-line regex finds nothing on exactly the
dumps whose include is long — which is every class pool; and "occurred
in ABAP program" arrives as "occurred inABAP program" when the wrapper
breaks there.

One thing the design did not ask for and the system offered: the
exception class is in both the structured attributes and the header
table. For `UNCAUGHT_EXCEPTION` and `RAISE_EXCEPTION` the runtime error
names only the mechanism, so the class is the part a person
recognises. It is named in the match reason when it agrees. It is not a
fifth rung; the ladder has four.

## The call graph, up and down

The dump names the program, the include and the line, and carries the
stack. From there `pkg/graph` is already the right tool — it has the
parser dependency extraction and the boundary analyzer:

- **down**: what does this code call, and which of those is where the
  bad value came from
- **up**: who calls this, and therefore who else is exposed to the same
  bug

That connects the graph engine to the debugger, which are currently two
unrelated priorities.

## Correlating logs: rank on structure, not on the clock

Time and user alone are a weak signal, and a tool that prints "the cause
was X" from a time join will be confidently wrong on its first hard
case — which is exactly when someone will believe it. Two things
happening in the same second is not causation.

But a log entry carries *the program that wrote it*, and that is not a
coincidence signal at all. If the writing program is the one that died,
or sits on the dump's own call stack, the connection is structural. That
reorders the whole thing: the clock becomes a filter, and the call graph
becomes the reason.

Ranked, strongest first:

1. **The log was written by the program that dumped.** The code that
   died said something on its way there.
2. **Written by a program on the dump's call stack.** The stack is in
   the dump; anything on it is on the causal path by construction.
3. **Written by something the failing line calls**, walking `pkg/graph`
   downward — a plausible source of the bad value.
4. **Written by a caller**, walking upward. Rarely the source; this is
   the blast radius, which is a different and also useful question.
5. **Same user, near in time, nothing structural.** A tiebreaker, and on
   its own barely evidence.

Two refinements that matter more than they look:

- **Direction, not just proximity.** A log written by a stack program
  *after* the dump is cleanup or error handling, not cause. Sorting by
  distance in seconds loses the sign.
- **The same reasoning applies to similar dumps.** Grouping by program
  and error type is structural; grouping by "same afternoon" is not.

Output stays candidates with the reason shown — "written by
ZCL_X, frame 3 of the dump stack, 0.4s before" — because the reason is
what lets a person overrule the ranking. "The cause" is still not ours
to say; the difference is that now most rows have an actual argument
behind them instead of a coincidence.## Order to build it

1. `vsp dumps` — list and group. Categories only, no HTML. Answers
   "what keeps failing" on day one and needs nothing else to exist.
2. `vsp dumps <id>` — one dump in detail, HTML parsed. Brittle by
   nature; isolated so its brittleness stays local.
3. Similar-dump ranking over the group index. **Done** —
   `vsp dumps --similar`, all four rungs, see above.
4. Graph up/down from the failing line, reusing `pkg/graph`. This
   moves ahead of log correlation, because it is what makes the
   correlation worth reading — without the stack and the graph there is
   nothing to rank on but the clock.
5. Log correlation, ranked on the graph. The sources are readable
   without RFC: the dump feed, the system log feed, and `BALHDR`
   through free SQL. Message bodies are the one thing that would need
   Z code, and the ranking does not depend on them.

Post-mortem debugging proper — attaching the debugger to a dump rather
than to a running program — belongs after these. It is a separate
choreography and the feed does not hint at it; whether ADT exposes it at
all still needs checking.

## Checked on three releases

Everything above was first built against 7.58 and then run on 7.57 and
7.50. What differs is one thing, and it matters:

| | 7.50 | 7.57 | 7.58 |
|---|---|---|---|
| `/runtime/dumps` feed — list, group | yes | yes | yes |
| `/runtime/dump/<id>` — detail, call stack | **no** | yes | yes |
| `BALHDR` through free SQL | yes | yes | yes |

7.50 has the dump feed and not the detail resource, so a dump's call
stack cannot be read there — the same shape as that release having the
debugger but no `/debugger/stack`. Neither the `/vit/` viewer path nor
the singular one answers; both are 404.

The correlation degrades rather than fails: the stack rung and the graph
rung below it go unused, and the remaining rungs still rank. It is
reported as `ErrDumpDetailUnavailable` and printed as a plain statement
rather than an error, because a release that simply lacks a resource is
not a fault and should not put an alarming line under every dump on a
healthy system.

The lesson repeats: **discovery does not list the dump resources at all**,
on any of the three, so what a release offers here can only be learned by
asking it.
