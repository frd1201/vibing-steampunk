# The graph audit, and what ZRAY already solved

## The audit

`docs/graph-guide.md` is honest. It promises three things — transport
co-change, reverse-dependency impact, and heuristic `TVARVC` config
usage — names its entry points, and states its limits without softening
them.

Checked live against 7.58, all three answer. One of them, `where_used_config`,
had **never** answered until today: its query asked `CROSS` for
`TYPE = 'DA'`, two characters in a `C(1)` column, and the 400 was read as
"nothing found". `'DA'` turned out to be a `WBCROSSGT` `OTYPE` — a
different table, a `C(2)` column, and a data object rather than a table —
so truncating it to `'D'` would have compiled and returned dialog
modules.

### The finding is the drift in the other direction

The guide documents **three** graph capabilities. The tool surface
exposes **thirteen**:

| documented | undocumented |
|---|---|
| `co_change` | `callers`, `callees`, `call_graph` |
| `impact` | `analyze_call_graph`, `usage_examples` |
| `where_used_config` | `analyze_deps`, `check_boundaries` |
| `references` | `graph_stats`, `object_structure` |

And every dead feature found today was in the undocumented column:
`callers` and `callees` and `object_structure` on a resource namespace
that does not exist, `usage_examples` asking for a two-letter code in a
one-character column and never returning a row in its life.

**Undocumented features are unaudited features.** Not because anyone
decided not to check them, but because nothing said they were supposed
to work, so nothing noticed when they did not. The guide's honesty about
its three protected those three; the silence about the other ten is what
let them rot.

That is a rule worth keeping: a capability that is exposed and not
written down has no promise to fail against.

## How ZRAY is built, and why it matters here

The ABAP side already solved problems `pkg/graph` has not reached.

**The store.** `ZLLM_00_NODE` / `ZLLM_00_EDGE`, and their `ZRAY_00_*`
counterparts, are a property graph with three design decisions worth
stealing:

- **`SEED`** — a crawl-run id on every node and edge. A re-crawl is a new
  seed rather than a destructive rewrite, so two snapshots coexist and
  can be compared. `pkg/graph` has no persistence at all, so it has
  never had to face this.
- **Containment lives in the node**, not in an edge: a node carries
  `ENCL_OBJ_TYPE`/`ENCL_OBJ_NAME`, so a method knows its class without a
  traversal.
- **Three booleans classify a node** — `IS_CODE_UNIT`, `IS_TYPE`,
  `IS_COMPOSITE`. That is exactly the distinction our `callees` had to
  invent today, deciding whether a row is an invocation or a type
  reference. It was already modelled.

**The engine.** `ZCL_XRAY_GRAPH`, ~1700 lines: `BUILD_DOWN` / `BUILD_UP`
and their saving variants, `PROCESS_DOWN` / `PROCESS_UP`,
`IS_END_OF_RECURSION` for termination, `UPDATE_PROCESSED_ID` for the
visited set, and per-kind extraction (`CLASS_TO_NODE`, `CLASS_TO_EDGE`,
`_TRANSACTION_TO_NODE`). A bidirectional crawler with the two things a
crawler needs and usually lacks: a stop condition and a visited set.

**The traversal is a strategy, not a shape.** `ZCL_RAY_10_SPIDER`
exposes `bottom_up`, `top_down` and `flat`, and `apply( io_step, iv_mode )`
takes the mode as a parameter *and the step as an injected object*. The
step is an LLM call. `ZRAY_10_SPIDER` — the report — is 170 lines,
almost all of it a selection screen, choosing a prompt by name
(`document`, `bug-json`, `package`) and a direction.

So the "external agent" idea is not a proposal. It is already running in
ABAP: a graph traversal whose direction is a parameter and whose work at
each node is an injected LLM step.

## What follows

Today's evidence says the traversal is where things break, and ZRAY says
the traversal is the part that should not be fixed in code at all.
`max_depth` was removed from the call-graph tools this week because both
sources are one hop and depth was never real — a fixed strategy that was
fiction. That is the same lesson from the other end.

**The primitives are the product; the walk is the part that keeps being
wrong.** Good primitives look like: who calls this, what does this call,
what reads this table, what changed with this, what encloses this. Each
is one hop, each is checkable, each can say honestly that it could not
answer. The walk — how deep, which direction, when to stop — is a
decision that depends on the question, and an agent can make it per
question where a Go function cannot.

Order, and none of it is extraction yet:

1. **Write down the ten undocumented capabilities** — what each answers,
   from which source, and what it cannot see. Undocumented is unaudited,
   and this is the cheap half of not repeating today.
2. **Make each primitive state its own blindness in its answer**, the way
   `callees` now does ("references recorded at activation, not observed
   calls"). Six of the thirteen still do not.
3. **Then** ask what a traversal layer should look like, with ZRAY's
   seed/containment/classification model in front of us rather than
   reinvented.

Extraction is a later question. Freezing an interface around a surface
where ten of thirteen features were undocumented and four were dead
would freeze the wrong thing.
