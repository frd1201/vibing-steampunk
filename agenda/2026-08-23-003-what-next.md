# What deserves the next sprint

Written after v2.44.0, with the day's evidence still fresh.

## The recommendation

**Hunt the silent-failure class.** Not because it is glamorous, but
because today produced five of them and every one had the same shape:

- MCP's dump filters were ignored by the resource; all six were decoration.
- Its feed parser read fields that are empty on every row.
- `EXEC_RESULT` was matched with a prefix against a wrapped message, so it
  never matched — "no output captured" described every run there had ever been.
- `usage_examples` asked CROSS for a two-letter code in a `C(1)` column; the
  400 read as "nothing found", and that path had never returned a row.
- A correlation rung shipped the previous day could not fire, because the
  resource under it does not exist on any release we can test.

**An error swallowed as an empty result.** Five instances, one shape, and
**not one of them visible by reading the code** — each needed a live
system to find. That is not five bugs, it is a defect class, and the
codebase is full of places where a failed call becomes an empty list.

We also now have the technique, which we did not have this morning:
probe the live system, diff three releases, and record cassettes so the
answer stays. That is what makes this a sprint rather than a wish.

Two rules worth adopting while doing it:

1. **A caller that cannot tell "nothing found" from "the question
   failed" must not return an empty list.** Say which.
2. **Absence must be announced, not degraded past.** Degrading
   gracefully past something that is always missing is
   indistinguishable from working — that is exactly how the graph rung
   shipped dead.

## Fold in: the mode gap

The universal `SAP()` tool exists only in hyperfocused mode, so agents in
`focused` and `expert` cannot reach the seven post-mortem types or the
four AMDP targets at all. It is the same disease — a capability that
looks present and is not — and it is a day of work, not a sprint. Do it
inside the above.

## The installer question, corrected

An earlier version of this note said two things still need ZADT_VSP:
stateful RFC and "git export". The second half was wrong twice over —
the Z service does import as well, and what it buys is not the ability
but the **breadth**.

`vsp copy` is explicit about it: the native ADT path handles **six**
object types, hardcoded — PROG, CLAS, INTF, DDLS, BDEF, SRVD — and the Z
path handles whatever abapGit does, around 158. And it does not
implement them: `ZCL_VSP_GIT_SERVICE` calls
`zcl_abapgit_objects=>supported_list( )` and delegates.

So the real dependency is not our Z package. It is **abapGit**, and
ZADT_VSP is a bridge to it:

```
full-coverage import/export → ZCL_VSP_GIT_SERVICE → abapGit (full) → ?
```

The routing table still holds for everything else: read, edit, debug,
AMDP, table reads, module lists and transports are all plain ADT, and
stateful RFC is genuinely ZADT_VSP because SOAP-RFC cannot hold a
session.

### The circle, and where it breaks

To install abapGit full — roughly a thousand objects across many types —
you want full-coverage import. To have full-coverage import you need
abapGit full. That circle is why a lean receiver was proposed at all.

The way out is sharper than it looked. The native six include **PROG and
CLAS**, and a program can be created on a bare system over plain ADT with
nothing installed — verified today, twice, on two releases. So:

- **abapGit *standalone* can already be installed with zero Z code.** It
  is a single report. But it exposes no global classes, so nothing can
  call it — established in
  [2026-08-22-003](2026-08-22-003-lean-installer.md).
- **Therefore the lean receiver must itself be a report or a class**, and
  nothing else. Not a function group, not a package of objects — those
  cannot be installed by the six types, and building a receiver that
  needs a receiver is the circle again.

That is the design constraint the earlier note was missing, and it is a
real one: it rules out most of the shapes such a thing could take.

### What to decide, and in what order

1. Confirm that a class deploys over plain ADT to a bare system the way a
   program does. Everything below rests on it.
2. Then choose: a general `MonoUniAbapGitRFC`, or a receiver whose only
   job is to unpack a ZIP and install abapGit full. The second is
   smaller, and the first is the second plus a general API we have no
   demonstrated need for yet.
3. Only then ask whether the six native types should grow. Every type
   added is a serializer we maintain and abapGit already has — but every
   type added is also one less reason to need abapGit at all.

Nothing here should be built before step 1 is checked. Building a
bootstrap for a dependency whose shape we had wrong is how this note
started.

## Then: the Lua-driven debugger, as the article's centrepiece

A statement-level ABAP trace with values, driven by a Lua script, with
nothing installed on the server and no Eclipse anywhere — that is a
demonstration, and it belongs with the writing rather than before it.
The material is now real: self-repairing SSO, RFC with no gateway and no
password, a debugger that works on a release that has no stack resource,
an AMDP breakpoint that fires, and five silent failures found by asking
the system instead of reading the code.

  `cache` connect — decided and not executed.

  conformance stays a runtime probe rather than a fixture.
