# Should we retire the non-hyperfocused modes?

**Author:** claude-mac-m2
**Date:** 2026-08-22
**Status:** recommendation, not yet decided

## The question

vsp exposes its ABAP surface through three MCP modes — `focused`, `expert`,
`hyperfocused` — plus a CLI with its own commands. Should the first two go, so
that CLI, MCP and the handlers can never disagree?

## What is actually there

Measured on `main` at the time of writing, not read off the docs:

| | count |
|---|---|
| tools passed through `shouldRegister(...)` | **153** |
| names in the `focused` whitelist | **102** |
| dead entries in that whitelist (listed but never registered) | **0** |
| `register*Tools` groups | 23 |
| `route*Action` functions the universal tool chains through | 27 |
| `tools_register.go` + `tools_focused.go` | ~2600 lines |

Two things follow immediately.

### The counts in the docs are already wrong, in three different ways

- `cmd/vsp/main.go:40` — "81 tools (focused), 122 (expert)"
- `cmd/vsp/main.go:142` — "focused (100 tools) ... expert (147 tools)"
- `README.md` — 100 / 147, repeated in six places

Actual: **102 focused, 153 registered.** Three numbers, none of them right, in
one binary. Nobody is lying; the numbers simply cannot be kept true by hand,
and no test checks them. This is the drift the question is about, already
happening, in the cheapest possible place to notice it.

### There is no structural link between the two dispatch paths

Individual tools are registered by 23 `register*Tools` groups. The universal
tool dispatches through a chain of 27 `route*Action` functions. The two sets do
not correspond — 8 register groups have no same-named router, 11 routers have
no same-named group. Some of that is naming (`Dev` vs `DevTools`, `File` vs
`FileIO`, `Edit` vs `Source`), but the point stands: **adding a capability to
one path does not force it into the other, and nothing fails if you forget.**

### The two paths already behave differently

Found the hard way this session, not by reading code:

- `SAP(action="query", params={"sql": ...})` answers *"No handler found for
  action=query"* even though `query` is in the tool's own list of valid
  actions. It needs `target="SQL"` and `params.sql_query` — a convention that
  exists only in the universal surface's help text.
- `RUN_REPORT` takes its selection-screen values in `params` (a JSON **string**
  inside the params object), not `parameters`. Passing the wrong key is not an
  error: the report runs with defaults. That cost a 120-second timeout and a
  wrong conclusion before the mistake was visible.

Both are consequences of the universal tool taking `params` as an untyped
object. Individual tools have typed, per-tool schemas; the universal tool has
prose.

## Recommendation

**Yes to converging on one surface, but not by deleting code first.** Three
steps, in this order.

### 1. Add the parity test now (blocks nothing, catches everything)

A test that enumerates every capability once and asserts it is reachable
through the universal router. Whatever the list is derived from — the
`register*Tools` groups today — becomes the single source of truth, and a
capability that exists in only one path fails the build.

This is worth doing **even if the modes stay**, and it must land before any
deletion: right now, deleting `tools_register.go` would silently drop any
capability whose universal router is missing, and we would find out from a
user.

The same test should assert the documented counts, so `main.go` and `README.md`
cannot drift again. A number in prose that no test reads is a number that will
be wrong.

### 2. Deprecate `focused` and `expert` — do not delete them yet

This is a public repository with users and open pull requests against these
files. Removing a documented `--mode` is a breaking change:

- keep the flag working, print a deprecation notice naming the removal version
- point the docs at `hyperfocused` (already the **default** in
  `cmd/vsp/main.go:142` — the other two are opt-in paths)
- remove in the next major

### 3. Then delete, and only then consider the CLI

Retiring the two modes removes ~2600 lines and one of the two dispatch paths.
That is the real prize: after it, "add an MCP tool" is one edit instead of
three (`tools_register.go` + handler + `tools_focused.go`), and the focused
whitelist stops being a thing anyone can forget.

The CLI is a third surface, and converging it is a separate, larger job: its 28
commands call `pkg/adt` directly rather than going through the routers. Doing
that after step 3 is coherent; doing it at the same time is not.

## The argument against, stated fairly

The universal tool trades typed schemas for prose. With 153 individual tools, a
client sees each tool's parameters and the wrong key is rejected before the
call. With one tool taking `params: object`, the wrong key is accepted and
something plausible-but-wrong happens — exactly the `parameters` / `params`
trap above.

So the honest version of the recommendation is: converge on one surface **and
put the types back**, per action, on the universal tool. Without that, this
trades a maintenance problem for a correctness problem, and the correctness
problem is the more expensive one — it is paid by whoever is debugging at the
time, silently.

Discovery is the smaller half of the same issue: with one tool the model finds
capabilities through `help` rather than through the tool list. That is a real
cost in tokens-to-first-correct-call, and it is the cost hyperfocused was
introduced to trade against (~200 tokens of surface vs ~40K).

## What I would do

1. Parity test + counts asserted — this week, independent of the decision.
2. Typed per-action params on the universal tool — the prerequisite that makes
   the rest safe.
3. Deprecation notice on `focused` / `expert`.
4. Deletion in the next major, then the CLI convergence as its own project.

Steps 1 and 2 are worth doing whatever is decided about the modes. If the
answer to the original question turns out to be "no", the work is not wasted.
